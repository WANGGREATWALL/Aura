# B3：统一等待、单查询者与 worker 退休

日期：2026-10-20～21 UTC。源码起点 `900a738`，本批本地改动尚未提交、未推送。完整问题列表在 [整改计划](../flow_remediation_plan.md)。目标设备、NDK 与 FlashPE 验证仍按用户决定后续执行；主机模型结果不代替真机功耗或 GPU 性能验收。

## 最终行为

- 工作许可仅对应 Ready/Completion 队列项。控制通知增加独立世代，shutdown 不再 post(8) 制造许可。等待入口在同一 mutex 下检查许可、世代和期限；世代快照使用 acquire 读取，睡眠前在 mutex 下重新检查。
- 普通等待者的 CV 同时接收工作和控制；超预算 worker 使用同一个入口/同步状态下的 parked CV，只接收控制与期限。控制广播两者，工作只 notify_one 工作 CV。这样不会让超预算等待者吞掉工作通知，也不需要原子等待两套独立通道。
- 协作 Task wait 和 helper join 登记到目标的等待者计数；登记和终态发布共用目标 mutex。完成后增加 gate 世代，睡眠前重查终态；不再靠 1 ms 周期取得进度。队列发布暂不可见时，最多探测 8 次，退还真实许可并重查目标/控制/期限，避免在持有许可的内部循环中永久自旋。
- 只有一个空闲 worker 持有周期查询者身份。它轮转扫描全部挂起完成，每批最多查询 8 条；未完成的一轮继续推进，完整轮次之间退避，进展后缩短间隔。它在运行普通工作、超出预算或退出前交接身份；协作 Task/helper/fence 等待返回用户 CPU 代码之前也必须交接。释放身份与退休裁定通过 worker mutex 串行化；到期的空闲消费者发现仍有挂起事件且身份无人持有时先接管，避免在忙碌线程后方全部退休。初次完成队列处理、显式外部 fence wait 和正常 wrapper 入口仍可以主动查询；没有把这些活动调用伪称为唯一查询者。
- 托管 fence 的 worker 等待使用同一 gate，可协作执行其他工作；达到深度上限时回退为主动查询，保持设备完成进度。显式外部等待保留在调用线程上完成查询/清理的能力。standalone fence 活动等待采用有界退避/CV；同一 registry 只有一个 drain 调用者定时查询，其他 drain 等待完成。上述代码没有固定 1 ms sleep。
- 亲核策略的原子版本先做快速比较；仅版本变化才复制/应用策略。扩容移到发布/需求变化侧，普通 dispatch 不再无条件锁 worker mutex 扩容。需求包括一个必要的挂起查询消费者，避免查询者运行 CPU 工作后无人接管。join 解锁期间可能改变预算，扩容每轮重新读取当前需求。
- worker 默认空闲 2 秒退休，最终常驻为 0。存在挂起 GPU 工作时保留推进者；未接受完的提交以及未完成任务不能失去最后一个可用消费者。纯外部同步 Job 没有 helper 时不需要保留 worker，其 caller 生命周期仍由 Job 计数覆盖 shutdown。

## 接受、槽位与关闭协议

| 边界 | 保持的不变量 |
| --- | --- |
| 提交开始到发布结束 | WorkerAdmission 在 worker mutex 下保留存活资格；通用 Task/helper 接受、队列发布完成前不会让最后一个消费者退休。首线程创建失败仍在接受前报告，helper 仍可退化为 caller |
| 退休裁定 | 持 worker→graph 锁检查 admission、accepted Task、查询 pin；所检查计数的写入者负责唤醒已到退休期限的等待者。普通任务/Job 不通过假工作许可通知 |
| 槽位复用 | Free → Running → Retiring → Exited → Joining → Free；稳定 slot ID，重建时 generation 增加。old thread 在复用前 join，join 不持 graph/worker/gate/provider mutex |
| 查询亲核性 | 读取活跃 slot 的 TID 并 pin 当前代际；native 查询在锁外执行，pin 释放后才可退休/复用。旧 snapshot 不代表永久线程身份 |
| 关闭 | 先 Stopping 并排空 Task/Job，再阻止新 admission/亲核查询，等待 admission/joiner/query pin 退出，控制广播并在锁外 join 全部 worker |

新增锁关系只涉及本批协议：worker→graph，graph/worker/external→gate；gate 的等待谓词不反向获取任何调度器锁。Node/CompletionState 的等待计数与完成发布共用各自 mutex，发送完成控制时不持这些目标 mutex。驱动、用户回调、销毁和 join 不在上述调度锁下执行。完整 mm/graph/diagnostics/slab 锁审查仍属于 B4，不能据此关闭整个 R19。

`getWorkers` 现在枚举存活槽位，ID 可不连续；已退休 slot 的亲核查询返回 NotReady，线程重建后 TID 可以改变。公开结构布局和 ABI 版本不变，头文件已说明迁移边界。测试不再假定 snapshot 数组下标等于永久 worker ID。

## 验证与测量

实际结果如下；全部五轮测量、旧版失败样本、源码/二进制哈希和日志位置见 [原始数据与 manifest](B3-2026-10-20-data.json)。测试钩子和运行时计数只存在于 aura_testing；生产库仍不包含故障/时序钩子。超时计数是内部 wait_until 的返回次数，可能包含已到期而未实际睡眠的期限，**不是 OS/设备唤醒次数**。

新增运行时用例覆盖：控制世代不消费许可、超预算停车不吞工作通知、睡眠前发布/完成、暂停队列发布者、无 helper Job 与空闲退休、亲核查询 pin、接受前保留消费者、最后 slot 退休时新提交、周期查询单一领导者及预算/CPU 交接。混合压力每轮 4 个并发提交者，累计 2,000 个根任务及 5 次真实 2 秒退休/重建，并发修改策略、查询 TID 亲核性，验证计算总数与完成。

另扩展托管/standalone fence 的单 worker 协作、深度上限完成、多个 fence wait/drain 恰好一次清理；保留原有主机线程显式查询/清理、原生来源、双 so、关闭及故障场景。

本批不引入 OpenCL 完成回调、不改变普通 GPU DAG 完整完成边，也没有修改队列/池机制以掩盖 X13。B4–B7 的结构整理、接口完善、机制取舍和最终验收继续追踪。

### 生产测量方法

固定基线为 `900a738` 的 B2 二进制/静态库，候选为本批未提交源码。CPU 微基准源码 SHA256 保持 `54de32f3350f7eba159dbb8feb7c3989668ad1aeb418470e905e04ab5e55ce3f`。新增 idle 基准使用完全相同源码分别链接冻结 B2 库、B3 库和 B3 固定间隔实验库；固定间隔实验只把 Core 查询期限的最小/最大值均改为 1,000 µs，不进入生产源码。

五轮交错执行，测量时没有并行运行本批构建或测试。GCC 14.2、Release `-O3 -DNDEBUG`、正常 `aura`、CPU-only、trace/perf 输出关闭。主机 AMD EPYC 9V74，允许 CPU 0–4、cgroup 配额 4 CPU；未固定频率，共享主机波动仍然存在。不能将小样本中位数当成统计显著收益或设备承诺。

```sh
cmake -S . -B build/flow-b3-release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF -DAURA_BUILD_TESTS=OFF -DENABLE_OPENCL=OFF -DENABLE_FLOW_BENCHMARKS=ON
cmake --build build/flow-b3-release -j 2
./build/flow-b3-release/flow_microbenchmark
./build/flow-b3-release/flow_idle_benchmark
```

`flow_microbenchmark` 每项 16 次预热、101 个耗时样本，另用 25 次调用统计全局 C++ new；它不覆盖 malloc/驱动分配。idle 基准使用模型事件，各窗口 200 ms，最终空闲快照在 2,300 ms；记录进程 context switch，**不声称测得 OS 唤醒或耗电**。旧版 waitFor 超时后通过真实 CPU Task 恢复以安全收尾，该轮仍以 7 退出并记为失败，不能把恢复后的耗时当正常完成延迟。

### 查询、进度与退休结果

下表为五轮独立进程的中位数。最终五轮 B2 有 1 次完成停滞，B3 两种间隔均 5/5 正常完成。B2 的完成延迟仅统计 4 个有效样本；完整失败输出没有剔除。预算窗口的查询/context switch 中位数包含 B2 的失败样本，不可据其零查询解释成功耗收益。

| 指标 | B2 基线 | B3 单查询者、固定 1 ms（实验） | B3 单查询者、200–2000 µs（保留） |
| --- | ---: | ---: | ---: |
| GPU 模型在途，200 ms 查询次数 | 590 | 185 | 97 |
| 同窗口进程 voluntary context switch | 596 | 186 | 98 |
| 预算降为 1，在途 200 ms 查询次数 | 185 | 186 | 98 |
| 同窗口进程 voluntary context switch | 230 | 195 | 106 |
| 模型 ready 到 Task 终态，µs | 847.970（4 个有效） | 577.061 | 1090.451 |
| 空闲 2.3 秒后 worker / 进程线程数 | 4 / 5 | 0 / 1 | 0 / 1 |
| 同时点进程 PSS，KiB | 1629 | 1648 | 1648 |
| 恢复后首个任务，µs | 74.272（线程保留） | 141.824（重建） | 143.537（重建） |

B3 自适应间隔相对固定 1 ms 将本模型的周期查询约减半，但完成延迟中位数增加约 0.51 ms；五轮 ready→终态范围分别为 0.416–2.145 ms 和 0.027–2.161 ms。这包含主机调度、查询、清理与完成发布，并非 GPU 设备执行耗时，也不是调度器 2 ms 的硬时延保证。保留 200–2000 µs 退避作为当前默认候选，真机若不满足帧/尾延迟预算，应按同一方法调整上限或选择固定单查询者方案；这项设备取舍仍是 USER_VALIDATION。

纯空闲窗口三个版本均为零模型查询，context switch 中位数均为 1（包含基准自身 sleep）；没有把退休带来的线程减少说成 PSS 减少。B3 PSS 中位数从空闲前 1641 KiB 到退休后 1648 KiB，未下降；libc 可能保留线程栈等内存。2 秒退休也确实带来重建成本，上表同时保留此代价。

新增 **X14**：旧版 B2 在预算降低后可能不再推进挂起事件。最终 5 轮有 1 轮超过 5 秒，早期同一冻结基线的 5 轮另有 4 轮，均需真实 CPU 工作才能恢复；早期还有一次 20 秒测量超时。所有结果保留为补充数据，不与最终源码的 CPU 计时混合。B3 用控制广播、领导权释放/接管、必要消费者创建，以及退休裁定串行化处理该风险；runtime 竞争测试、托管 fence 返回后续查询测试和生产模型都验证了主机进度。有限测试并非并发正确性证明或设备驱动保证。
